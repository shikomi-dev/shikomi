# 設計原則

設計の名前を一つ選んで全部を説明しません。違う問題を解く考え方は、別の軸として重ねます。

## 貫く基準: 投資を複雑さと戻しにくさで測る

単純な機能を何層もの構造で固めません。業務規則が厚い、変更が多い、失敗時の影響が大きい場所へ、必要な分だけ構造を足します。

初めは単純でも複雑さは増えます。変更のたびに現在の構造で安全に受け止められるかを見直します。内部の命名や分割は安く戻せますが、公開API、保存形式、外部との契約は戻しにくいため、根拠と確認を揃えてから決めます。

## 分割: 変更を機能の中へ閉じ込める

一緒に変わるものを近くへ置き、機能どうしを離します。画面、サービス、モデルのような技術的な種類だけで横へ分けず、利用者が行うことの単位で縦に分けます（Vertical Slice、機能単位の縦割り）。

トップ階層を見て、使っている道具ではなく、このシステムが何をするか読める状態を目指します。共通化によって機能どうしが強く結び付くなら、小さな重複を残す方が安全なこともあります。

## 実行単位: バックエンドと利用先を独立させる

独立して配備する処理は `backend/<サービス>`、独立して配布する利用先は `client/<製品>` に置きます。一つのサービスや製品は、依存関係、起動、検査を自分の中へ持ちます。Web、モバイル、CLIを増やしても、それぞれが別の利用体験と配布周期を持てます。

単位どうしは相手の内部実装を直接読み込まず、`contracts` に公開した通信の約束を使います。データの持ち主もバックエンドごとに明確にします。これにより、同じリポジトリで開発を始めても、必要になった単位だけを後から取り出せます。

ただし、ディレクトリ分割はマイクロサービス化そのものではありません。別々の配備、データ所有、障害の分離が必要でないうちは、一つのリポジトリと一つの運用で扱う方が単純です。通信や運用の費用を払う理由が生まれたときだけ分離します。

## 依存方向: 業務の規則を外部技術から守る

複雑な機能では、画面、CLI、通信、データベースなど外側から、利用の手順、業務の規則へ依存を向けます。業務の規則は、保存方法やフレームワークを知りません。

これはクリーンアーキテクチャ（中心の規則を外部技術の変更から守る構造）の役割です。単純な値の受け渡しへ形式だけの層を増やしません。

## モデル化: 業務の概念をコードへ写す

型とメソッドには、業務で人が使う言葉（ユビキタス言語）を使います。データを外へ取り出して判断せず、判断と状態変化をその概念へ命令します。不正な状態は後で弾くより、できるだけ表せない形にします。

これはドメイン駆動設計（業務の言葉と規則をコードの中心へ置く設計）の土台です。集約、値オブジェクト、リポジトリなどの重い道具は、規則が厚い領域だけで使います。薄い処理は、読みやすい手続きとして書いて構いません。

## 読み順: 入口から一段ずつ詳しくする

どの構造でも、入口を開けば中心の利用の流れが上から読めるようにします。同じ粒度のメソッドを並べ、呼ばれた先が一段だけ詳しくなります。

この読み順はDDDやクリーンアーキテクチャの代わりではありません。DDDは概念、クリーンアーキテクチャは依存方向、トップダウンの段は読む順番を受け持ちます。詳しくは[実装構造](020_code-structure.md)を参照してください。
