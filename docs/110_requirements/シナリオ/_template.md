# SC-番号: 利用者の目的を表す名前

> `SC-番号-目的名/README.md` として使い、同じディレクトリに `_acceptance-template.md` から `受入例.md` を作る。

## 文脈

| 項目 | 内容 |
|---|---|
| スコープ | このシナリオの責任を持つシステムまたは製品 |
| レベル | 原則は「利用者の目的」。共通部分を別に切り出す場合だけ「サブユースケース」 |

## 概要

利用者が何のために、何を達成するシナリオかを書く。

## アクター

- 主アクター:
- 関係する立場と利益: 利害が複数ある場合だけ、誰が何を守りたいかを書く。無ければ「なし」

## 事前条件

シナリオを始められる条件を書く。無ければ「なし」。

## きっかけ

利用者または外部の何が、このシナリオを始めるかを書く。

## 入力

| 入力 | 必須 | 省略した場合 | 受け付ける値 |
|---|---|---|---|
|  |  |  |  |

## 入口別経路

| 入口 | 利用者の入力 | 成功時に見える結果 |
|---|---|---|
|  |  |  |

## 最低保証

失敗しても必ず守る状態を書く。例: 一部だけ保存しない、成功したと表示しない。

## 成功時保証

目的を達成した後に、外から確かめられる状態を書く。

## 主成功シナリオ

1. 最も一般的な成功の流れを、入口の技術へ寄せずに書く。

## 拡張

基本の段番号へ条件を結び、代替経路と例外経路を同じ場所へ書く。

- 2a. 同じ成功時保証へ進む別の正常値なら、処理を書いて戻る段を示す。
- 2b. 目的へ到達できない場合は、理由、返す結果、変えない状態を書いて終了する。

## 特別な要件

性能、監査、安全性、操作可能時間など、このシナリオで外から確かめる品質条件がある場合だけ要求または横断的な受入条件を参照する。無ければ「なし」。

## 技術・データのバリエーション

同じ入口でも形式や媒体が複数ある場合だけ書く。内部実装の候補は書かない。無ければ「なし」。

## サブユースケースと拡張点

別シナリオとして再利用する流れ、または後から差し込める目的を置く場所を書く。無ければ「なし」。

## 関連情報

対応する要求、同じディレクトリの受入例、横断的な受入条件、システムのシーケンスを指す。

## 備考

現在の範囲と、見落としと区別する必要がある対象外を書く。無ければ「なし」。
