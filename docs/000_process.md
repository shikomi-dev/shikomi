# 開発の進め方

小さな変更を、利用者の困りごとから実際の確認まで通します。同じ説明を各工程へ写しません。

## 何をどこに書くか

| 内容 | 正本 |
|---|---|
| なぜ必要か、誰のためか、製品の範囲 | `110_requirements` の背景・利用者・要求 |
| 目的、操作の流れ、成功と失敗で守る条件 | 目的ごとのシナリオの `README.md` |
| 具体的な入力と期待結果 | 自動ならテストのCSV等、手動なら確認書 |
| 受入ケースを探して実行する入口 | シナリオの `受入例.md` |
| 複数機能にまたがる構造・処理順・データ所有 | `150_system` |
| 今回変えることと、なぜその設計にするか | Issueと `210_increments/INC-<Issue番号>.md` |
| 実際に確認した結果 | PR |

受入条件はシナリオの成功時保証・最低保証に置きます。同じ条件をAC、SPECなどの別台帳へ書き直しません。具体値も受入例の文書とCSVへ二重に持たず、受入例は目的と実行先だけを示します。

## 一回の変更

1. Issueに困りごと、変えたい体験、対象外、完了条件を書く。実際の入力と期待結果は、テスト設計ができたらその正本を参照する。
2. Issue番号が決まったら増分の雛形を写す。今回変える範囲と設計理由を書き、外からの確認と境界の確認を対にする。既存仕様を丸ごと写さない。
3. シナリオから正常・代替・例外・境界の具体例を選び、CSVまたは手動確認書へ置く。環境の準備と後始末も決める。
4. 利用者の入口から一つの流れを通して実装する。関係する現在像だけを同じPRで更新する。
5. `just check` と実際の操作で確認し、PRへ結果を残す。

未実装の案はIssueで扱います。既定ブランチのシナリオは、今提供している体験を表します。

## 小さな変更を小さく保つ

CSVの値だけが変わるならCSVと、それに必要なコードだけを直します。ケースを追加するならCSVと受入例の一覧を直します。シナリオの保証自体が変わる場合にだけシナリオを更新します。

構造や保存形式が変わらなければsystem文書は変更不要です。「変更なし」を全ファイルに追記しません。例外なく全工程の文書を編集することを完了条件にしません。

設計はコードから自明なら増分に理由を一行書けば足ります。公開契約、移行など戻しにくい判断だけを決定記録へ分けます。

## 現在像と変更記録

現在のシナリオ・テスト・システム説明を更新します。完了した増分はその変更の記録として残し、後続のテスト改名や機能削除に追従させません。当時の実装は対応PRの差分とコミットから確認します。

自動検査は現在の受入例から個別テストまでを追います。過去の増分はIssue番号だけを検査し、現在の要求やテストへ参照が残ることを強制しません。
